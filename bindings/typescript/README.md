# typescript JS

JS library for interacting with [Soroban](https://soroban.stellar.org/) smart contract `typescript` via Soroban RPC.

This library was automatically generated by Soroban CLI using a command similar to:

```bash
soroban contract bindings ts \
  --rpc-url INSERT_RPC_URL_HERE \
  --network-passphrase "INSERT_NETWORK_PASSPHRASE_HERE" \
  --contract-id INSERT_CONTRACT_ID_HERE \
  --output-dir ./path/to/typescript
```

The network passphrase and contract ID are exported from [index.ts](./src/index.ts) in the `networks` constant. If you are the one who generated this library and you know that this contract is also deployed to other networks, feel free to update `networks` with other valid options. This will help your contract consumers use this library more easily.

# To publish or not to publish

This library is suitable for publishing to NPM. You can publish it to NPM using the `npm publish` command.

But you don't need to publish this library to NPM to use it. You can add it to your project's `package.json` using a file path:

```json
"dependencies": {
  "typescript": "./path/to/this/folder"
}
```

However, we've actually encountered [frustration](https://github.com/stellar/soroban-example-dapp/pull/117#discussion_r1232873560) using local libraries with NPM in this way. Though it seems a bit messy, we suggest generating the library directly to your `node_modules` folder automatically after each install by using a `postinstall` script. We've had the least trouble with this approach. NPM will automatically remove what it sees as erroneous directories during the `install` step, and then regenerate them when it gets to your `postinstall` step, which will keep the library up-to-date with your contract.

```json
"scripts": {
  "postinstall": "soroban contract bindings ts --rpc-url INSERT_RPC_URL_HERE --network-passphrase \"INSERT_NETWORK_PASSPHRASE_HERE\" --id INSERT_CONTRACT_ID_HERE --name typescript"
}
```

Obviously you need to adjust the above command based on the actual command you used to generate the library.

# Use it

Now that you have your library up-to-date and added to your project, you can import it in a file and see inline documentation for all of its exported methods:

```js
import { Contract, networks } from "typescript"

const contract = new Contract({
  ...networks.futurenet, // for example; check which networks this library exports
  rpcUrl: '...', // use your own, or find one for testing at https://soroban.stellar.org/docs/reference/rpc#public-rpc-providers
})

contract.|
```

As long as your editor is configured to show JavaScript/TypeScript documentation, you can pause your typing at that `|` to get a list of all exports and inline-documentation for each. It exports a separate [async](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function) function for each method in the smart contract, with documentation for each generated from the comments the contract's author included in the original source code.
# TypeScript bindings — generated, vendored

This directory holds the TypeScript bindings generated by
[`scripts/gen-bindings.sh`](../../scripts/gen-bindings.sh) from the
escrow contract's WASM. Vendoring the bindings here — next to the
contract, from the same WASM the deploys ship — is what makes the "one
versioned source" recommendation in
[`docs/ts-bindings-comparison.md`](../../docs/ts-bindings-comparison.md)
§4 literally true: the sibling `HarvestLock` app imports from the
exact file tree a reader can see here, not a tree it has to regenerate
locally to trust.

## How to update

```sh
# From the repo root.
scripts/gen-bindings.sh
```

This rebuilds the WASM, invokes `stellar contract bindings typescript`,
and overwrites this directory's generated files in place (except this
README and the `.gitignore`, which document the directory itself and are
preserved across regenerations). A `.wasm-sha256` file is written
alongside the generated sources so a reader can tell which WASM a given
commit's bindings came from without re-running the build.

The script pins the stellar-cli version it expects (currently 28.1.0,
matching [`docs/ts-bindings-comparison.md`](../../docs/ts-bindings-comparison.md)
§1); override with `STELLAR_CLI_VERSION` for a deliberate upgrade, and
update the pin in the script, the doc, and the Reference section of the
top-level `README.md` in the same PR.

## Drift check

```sh
scripts/gen-bindings.sh --check
```

Regenerates the bindings into a temporary directory and `diff`s them
against this committed copy. A non-zero exit code means the committed
bindings no longer match the current WASM — either because `lib.rs`'s
public surface changed (correct fix: regenerate and commit) or because
the stellar-cli emission itself drifted (correct fix: bump the pinned
version and regenerate). CI wiring for this check is a maintainer
follow-up per the [PR template](../../.github/PULL_REQUEST_TEMPLATE.md)'s
"CI is maintainer-managed" note; the script itself is independent of
that.

## What's in here

After a generation run:

```
bindings/typescript/
├── .gitignore            # preserved across regenerations
├── .wasm-sha256          # written by the script; records the source WASM
├── README.md             # this file, preserved across regenerations
├── package.json          # emitted; depends on @stellar/stellar-sdk peer
├── tsconfig.json         # emitted
└── src/
    └── index.ts          # emitted; the spec and typed client
```

`node_modules/` and `dist/` are produced only when someone runs
`npm install` / `npm run build` inside this directory and are excluded
by the `.gitignore`. The `--check` mode in `scripts/gen-bindings.sh`
excludes the same paths so an installed-but-not-committed working copy
doesn't look like drift.
