# TS bindings vs. the app's hand-built ScVal maps — what `stellar contract bindings typescript` produces, and whether to adopt it

Issue #64 asked for a concrete cross-check: generate TypeScript bindings
for this contract, diff what they produce against the hand-built `ScVal`
encoders in the sibling `HarvestLock` app's `api/`
(`allocationMemberToScVal` in `api/src/server.ts:504`,
`oracleConfigToScVal` in `api/src/stellar/deploy.ts:147`), and land a
recommendation. This doc is that cross-check, with the byte-level
evidence.

Short version: **the two encodings are byte-identical today**, the
generated bindings structurally eliminate the two failure modes the
hand-written code already had to document, and the recommendation is to
adopt the generated spec-driven encoding for argument building — as a
follow-up PR in the `HarvestLock` repo, since that is where the
hand-built code lives.

## 1. How to reproduce

```sh
stellar contract build                       # produce the deployable WASM this repo gates on
stellar contract bindings typescript \
  --wasm target/wasm32v1-none/release/harvestlock_escrow.wasm \
  --output-dir /tmp/escrow-bindings --overwrite
cd /tmp/escrow-bindings && npm install && npm run build
node compare.mjs                             # the script below
```

The generated package (checked with CLI 28.1.0) depends on
`@stellar/stellar-sdk ^16.0.1`; the bindings embed the contract's own
spec (29 functions, 38 error cases for the current WASM — a count that
tracks `lib.rs` exactly, which is itself a useful regeneration check).

The comparison script is a standalone ~120-line file (kept out of this
repo deliberately — it belongs to the app-integration effort, not the
contract). It replicates the app's encoders verbatim, feeds the same
inputs through both paths, and compares XDR bytes:

- all **13 `initialize` arguments** (the app hand-builds the full
  argument vector — `initializeArgs`, `api/src/stellar/deploy.ts:169`)
- the **`set_allocation` members vector** (`Vec<AllocationMember>`)
- **`oracle_config = None`** (the `Option` path)

One naming note found while wiring this up: the generated bindings keep
the contract's **snake_case** argument keys verbatim
(`warehouse_operator`, `oracle_config`, …), while the app's own API
layer uses camelCase (`warehouseOperator`, `oracleConfig`). The ScVal
bytes are identical either way; it only matters when porting call sites.

## 2. The byte-level result

Inputs: a 32-byte member hash, `share_bps: 6000`, `OracleConfig` with
`denominated_amount: 500000`, `max_age_secs: 300`, the real Reflector
GBP oracle address, `price_asset: "GBP"` — the same shapes
`api/test/` and the live testnet walks already use.

```
== initialize: all 13 args, generated spec-driven vs hand-built ==
  MATCH  arg[0] buyer … arg[12] oracle_config        (13/13)
== initialize: oracle_config = None ==
  generated arg[12] switch: scvVoid                  MATCH
== set_allocation: members = Vec<AllocationMember>[1] ==
  MATCH  members Vec
  decode: {"member_hash": <Buffer 32 bytes>, "share_bps": 6000}
  u32(6000) wire fragment 0000000300001770 present in generated bytes: true
  wire order of member_hash < share_bps: true

ALL 13 initialize args + members vec BYTE-IDENTICAL
```

Two details the raw "MATCH" hides, decoded explicitly because they are
the two things the hand-written code has burned time on before:

- **`share_bps` is `SCV_U32`** (ScVal tag `3`, value `0x1770` = 6000) in
  the generated output — the spec knows the field is `u32` and the
  encoder cannot choose otherwise.
- **Map key wire order is `member_hash` → `share_bps`** (ascending
  symbol order — what the Soroban host requires of an `ScVal::Map`), and
  the `OracleConfig` map comes out
  `denominated_amount → max_age_secs → oracle_contract → price_asset`,
  same as the hand-built version's deliberate manual ordering.

## 3. Why the generated side is structurally safer

The app's two hand-built encoders exist for reasons that are documented
in their own comments, and both reasons disappear with the generated
path:

1. **The type-inference pitfall.** `nativeToScVal(6000)` does not know
   the contract wants `u32` — the app's comment at
   `api/src/server.ts:499` records the discovered failure ("defaults
   share_bps to u64, the contract wants u32") and its fix: spell out
   `{ type: … }` at every call site, forever, including every future
   field anyone adds. The generated encoder derives types from the
   embedded spec — the default *is* the contract's declared type.
2. **The manual-ordering pitfall.** An `ScVal::Map` with out-of-order
   keys is rejected by the host as malformed (not looked up by name).
   The app's `oracleConfigToScVal` comment records that this had to be
   re-verified when `OracleConfig` gained `denominated_amount`
   (Deployment 9) — every field addition is a re-sort-and-re-verify
   exercise. The generated encoder emits spec order by construction.

Both are the same deeper failure mode: **a hand-written encoder is a
copy of the contract's ABI that nothing mechanically keeps in sync.**
Its failure surfaces at transaction-simulation time on a deployed
instance, not at compile time. The generated bindings are that copy,
generated — plus typed read results (`Commitment` with all fields,
`Status`, the error enum with doc comments), which covers the second
half of the same problem: the app's `Commitment` interface has already
gone stale once behind a contract change (the 5 FX fields, fixed by hand
on 6 Sept 2026, per the app repo's `HANDOFF.md`).

## 4. Recommendation

**Adopt the generated spec-driven encoding for argument building, as a
follow-up PR in the `HarvestLock` repo.** Concretely, the minimal-change
version:

- Vendor (or CI-regenerate) the bindings package from the **same WASM
  hash the app deploys** (`ESCROW_WASM_HASH`), so encoders can never
  drift from the deployed instance — that hash is already the single
  source of truth for which contract build the app talks to.
- Replace `initializeArgs`'s hand-built vector and the set-allocation
  member encoder with `spec.funcArgsToScVals("initialize", args)` /
  `("set_allocation", args)` against that spec. This is the whole
  change — the app's own transaction assembly, multi-party signing
  (`submitMultiPartyCall`, staged proposals) and ScVal staging in
  Postgres are untouched, because only the *construction* of the
  argument `ScVal`s changes, not what happens to them afterward.
- Delete both hand-built encoders and their comments; the pitfall notes
  move to history, not to the new code.

Rationale, stated as a trade-off rather than an endorsement: the
hand-built encoders are **correct today** — proven byte-identical above
— and the generated alternative costs a dependency and a per-contract-
version regeneration step. What it buys is the elimination of a class of
bug that has already fired twice in this app's short history (the `u32`
inference; the `denominated_amount` re-sort), each time caught only
because someone re-verified against a live deployment. That's a thin
margin for an integration whose failures are silent at compile time and
expensive at settlement time.

If the team prefers to keep the hand-built encoders for now, the
fallback is cheap and worth doing regardless: add the comparison script
as a test (pin hand-built output against `spec.funcArgsToScVals` output
for the struct arguments) so the next ABI change fails a test instead of
a simulation.
